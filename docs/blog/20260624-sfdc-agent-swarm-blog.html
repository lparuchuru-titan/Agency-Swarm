Building an SFDC Agent Swarm for Cursor

How we turned a large Salesforce DX monorepo into a multi-agent agency — with a live FleetView dashboard, token-aware knowledge refresh, and plain-English delegation.

If you work on a mature Salesforce org — thousands of Apex classes, CPQ, custom LWCs, Jira epics, and multiple sandboxes — a single AI chat thread stops scaling fast. We built an SFDC Agent Swarm: a CEO-style orchestrator in Cursor, specialist agents with skills, a LangGraph planning pipeline, and a local FleetView dashboard so humans can see what the swarm knows and what it is doing.

The problem we were solving

A mature Salesforce DX repo is a real production-scale project: thousands of Apex classes, dozens of LWCs, CPQ, billing, and custom product models. Developers were already using Cursor, but:

  • Every session started cold — no shared memory of org context, Jira AC, or repo conventions.
  • One agent tried to do everything: Jira, architecture, Apex, deploy, QA, docs.
  • Knowledge scattered across Confluence, Google Sheets, Jira, and local explainers.
  • No visibility into which “skills” were stale or which specialist should handle a request.

We wanted something closer to an agency: a lead who routes work, specialists who stay in their lane, and a knowledge layer that refreshes without burning tokens every day.

What we built

Three layers work together:
  1. Cursor Agency — CEO rule + specialist subagents (.cursor/agency/, AGENTS.md)
  2. Knowledge Swarm — scans force-app/, indexes Jira/Confluence, syncs skill feeds
  3. LangGraph Orchestrator — plans multi-step delivery, writes work orders, publishes delivery summaries
A local dashboard — FleetView — ties it together at http://127.0.0.1:8765.

When to use the swarm

Use the swarm when…

  • A Jira epic spans metadata + Apex + LWC + manual data steps
  • You need retrieve → implement → test → promote with traceability
  • You want structured work orders before coding (orchestrator run)
  • Onboarding someone to a large repo — run codebase KB refresh first
  • You want HTML explainers or architecture docs from live code + Jira
  • Multiple sandboxes / org aliases — context must come from project config

Skip the swarm when…

  • One-line typo fix in a single open file
  • Quick SOQL or a single Apex method tweak you already understand
  • Production deploy without sandbox validation (swarm still needs human approval)
  • You only need a chat answer with no repo or org context
Rule of thumb: If you would ask a tech lead to “break this down and assign it,” use the CEO + orchestrator. If you would ask a teammate “what does this line do?”, stay in a single Cursor chat.

How to use it (day to day)

1. Plain English in Cursor (most common)

Open Cursor chat and describe the task like you would to a project lead:

Implement quote line editor enhancement for PROJ-1001.
Retrieve latest LWC from the sandbox, match Jira AC, then prepare promotion notes.

The agency-swarm-cursor rule (Apply Intelligently) acts as CEO and delegates to specialists. Editing files under force-app/ auto-attaches the Salesforce agency context.

Force CEO mode anytime: @agency-swarm-cursor

2. Resolve org context first

Never hardcode org aliases. Always:

sfdc-swarm context

This reads .sf/config.json in the project and prints targetOrgAlias, source path, and project root.

3. Run the orchestrator for multi-step delivery

sfdc-swarm orchestrate "Implement MAX bundle QCP changes and document verification steps"

Output lands in:

  • .cursor/swarm/.fleet/runs/<run_id>/ — PLAN, work orders per team
  • docs/swarm-deliveries/<run_id>-delivery.md — human-readable summary

Open the work order (e.g. work-apex-developer.md) and launch the matching Cursor subagent with that file as context.

4. Refresh knowledge (token-aware)

Weeklysfdc-swarm skill-refresh --tier weekly0 tokens — Jira/Confluence indexes via MCP checklists

FleetView — the live dashboard

FleetView is a local HTTP server (serve_fleet.py) that shows swarm health, skill feed coverage, active agents, orchestrator runs, and KB progress. It does not call Cursor APIs — it is the human control plane.

Start FleetView: sfdc-swarm serve then open http://127.0.0.1:8765/skills-fleet.html. Leave the terminal open while using it. Stop with: lsof -ti:8765 | xargs kill -9

How to implement this in your own Salesforce project

The framework is designed to be global (one install) and per-project (each DX repo gets its own KB and fleet state).

Step 1 — Install the global framework (once per machine)

cd tools/sfdc-knowledge-swarm
./install-global.sh
pip install -r requirements.txt

This copies the swarm to ~/.cursor/sfdc-knowledge-swarm and adds the sfdc-swarm CLI to ~/.local/bin.

Step 2 — Copy agency template into your DX repo

Your repo needs:

AGENTS.md                          # agency entry point
.cursor/agency/                    # manifesto, chart, per-agent instructions
.cursor/agents/*.md                # Cursor subagent definitions
.cursor/rules/agency-swarm-cursor.mdc
.cursor/rules/agency-swarm-salesforce-files.mdc
tools/sfdc-knowledge-swarm/        # project-local copy (or symlink to global)
knowledge-base/                    # per-project KB output
.cursor/swarm/.fleet/              # run state

Step 3 — Define specialists in the registry

Edit tools/sfdc-knowledge-swarm/agents_registry.py — map teams, agents, Cursor subagent names, skills, and MCP tools. Then sync:

python3 tools/sfdc-knowledge-swarm/agency_cursor_sync.py

Step 4 — Wire Cursor rules

  • Set agency-swarm-cursor.mdc to Apply Intelligently (not Manual)
  • agency-swarm-salesforce-files.mdc auto-attaches on force-app/ edits
  • Add global skills under ~/.cursor/skills/ (advanced-salesforce-developer, sfdc-metadata-sync, etc.)

Step 5 — Configure org resolution

Each project resolves its default org from .sf/config.json. Optional overrides in .cursor/sfdc-project/config.json. The CEO and all skills must call sfdc-swarm context — never hardcode org aliases or record IDs.

Step 6 — Optional: scheduled refresh (macOS launchd)

cp framework/launchd/com.agency-swarm.skill-refresh-daily.plist ~/Library/LaunchAgents/
launchctl load ~/Library/LaunchAgents/com.agency-swarm.skill-refresh-daily.plist

Daily = free static scan. Weekly = connected indexes. Monthly = small LLM budget for stale topics only.

Step 7 — Optional: MCP integrations

Connect Atlassian + Google Workspace MCP in Cursor for live Jira/Confluence/Sheets reads. The requirements team briefs reference these; without credentials, the swarm writes MCP checklists instead.

Architecture (two modes)

ModeEntryGraphOutput
Supervisor orchestrator sfdc-swarm orchestrate or FleetView Run Orchestrator plan → dispatch (requirements → design → dev → admin → QA → docs) → finalize Work orders + docs/swarm-deliveries/*.md
Codebase KB swarm sfdc-swarm dev-once or FleetView Run Swarm plan → ui_ux → sf_dev → sf_admin → index knowledge-base/codebase/*.md

Important design choice: Python LangGraph is the planning plane. Apex/LWC edits, deploys, and tests happen in Cursor via subagents and skills. The orchestrator produces structured handoffs — it does not replace the IDE.

Lessons learned

  • CEO delegation beats mega-prompts. Specialists with narrow skills produce safer Salesforce code (bulkification, FLS, retrieve-first).
  • Token-aware refresh matters. Daily static scans cost zero LLM tokens; reserve LLM for stale or ambiguous topics only.
  • FleetView builds trust. Developers adopt agents faster when they can see feed freshness and run history locally.
  • Org context must be automatic. Hardcoded aliases caused more deploy mistakes than any agent hallucination.
  • Work orders bridge planning and coding. The orchestrator’s markdown artifacts are the contract between “what to do” and “do it in Cursor.”
  • Inspired by Agency Swarm. We adapted the Agency Swarm + Cursor pattern for Salesforce delivery realities (CPQ, promotion repos, sandbox tracking).
